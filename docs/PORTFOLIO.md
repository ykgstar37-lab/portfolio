# SubFlow — 구독 관리 플랫폼

> 흩어진 개인 구독(Netflix·Spotify·ChatGPT 등)을 한곳에서 관리하고, 지출을 분석하고, 결제일·환율·중복 구독을 알려주는 **웹 + 모바일 풀스택 서비스**

| 항목 | 내용 |
|------|------|
| **역할** | 기획·설계·프론트(웹/모바일)·백엔드·배포 (풀스택 단독) |
| **기술** | React 19·TypeScript·Zustand / Expo·React Native / FastAPI·SQLAlchemy 2.0(async)·PostgreSQL 16 / Docker·nginx |
| **규모** | API 라우터 7개, DB 테이블 11개, 서비스 카탈로그 83종(12카테고리), 웹·모바일 클라이언트 2종 |
| **링크** | GitHub: github.com/hyebinhy/SubFlow |

*(기간·팀 구성·배포 URL은 실제 값으로 채워 넣으세요)*

## 1. 외부 구독 연동의 현실적 한계 → 카탈로그 기반으로 방향 전환

**문제**
"구독 관리 앱"의 이상은 사용자의 카드·앱스토어·카카오 결제 내역을 자동으로 긁어와 구독을 채워주는 것. 하지만 이게 실제로 가능한지 검증이 필요했다.

**의사결정**
플랫폼별 연동 가능성을 직접 조사(`INTEGRATION_RESEARCH.md`)한 결과:
- 앱스토어·플레이스토어·카카오톡 **전체 구독 목록 조회 API는 제3자에게 제공되지 않음**
- 카드사 결제 내역은 **마이데이터 사업자(금융위 인가)** 가 있어야 접근 가능
- 유일한 현실적 경로는 Gmail 영수증 파싱 / 각 기기의 IAP 조회뿐 → 개인 프로젝트 범위 초과

→ "자동 수집"을 포기하고 **사전 구축한 서비스 카탈로그에서 선택하는 방식**으로 제품 방향을 전환.

**해결 / 결과**
- 인기 서비스 83종(12카테고리)과 요금제(Basic/Standard/Premium)를 DB 카탈로그로 구축 → 사용자는 **검색 → 서비스 선택 → 요금제 선택**만으로 구독 등록
- 자동 수집 대신 **환율 변동·중복 구독·예산 초과·가격 인상 알림** 등 카탈로그 데이터로 만들 수 있는 "관리형 인사이트"에 집중해 제품 가치를 재정의
- 검증되지 않은 기능에 시간을 쏟기 전에 **실현 가능성을 먼저 조사해 방향을 튼** 사례

## 2. 수동 입력 UX 문제 → 카탈로그 + 요금제 모델로 재설계

**문제**
초기 버전은 사용자가 서비스명·금액·결제주기를 **직접 타이핑**하는 방식. 오타·표기 불일치로 중복 감지·지출 분석 같은 기능의 데이터 품질이 떨어졌다.

**의사결정**
기존 인증·분석·알림 코드는 유지하면서, `services` / `service_plans` 테이블을 추가하고 `subscriptions`에 `service_id`·`plan_id` FK를 연결하는 **점진적 마이그레이션**을 설계(`CATALOG_MIGRATION_PLAN.md`). 전면 재작성이 아닌 스키마 확장으로 리스크를 최소화.

**해결 / 결과**
- 정규화된 서비스/요금제 데이터 위에서 **카테고리별 중복 감지, 가격 인상 이력(`plan_price_history`), 로고·해지 링크 제공**이 정확하게 동작
- 구독 추가 흐름이 "타이핑"에서 "선택"으로 바뀌어 입력 마찰과 데이터 오류를 동시에 감소

## 3. 웹·모바일 코드 이원화 위험 → API-first 단일 백엔드

**문제**
웹(React)과 모바일(React Native)을 모두 지원해야 하는데, 비즈니스 로직을 양쪽에 중복 구현하면 유지보수가 두 배가 된다.

**의사결정**
설계 초기부터 **API-first 원칙**을 세우고, 지출 분석·중복 감지·환율 변환 등 모든 도메인 로직을 FastAPI **서비스 계층**에 두었다. 웹·모바일은 `/api/v1`을 소비하는 얇은 클라이언트로만 유지.

**해결 / 결과**
- React 웹과 Expo 모바일이 **동일한 백엔드·동일한 계약(JWT + Axios 인터셉터)** 을 공유 → 로직 변경 시 한 곳만 수정
- 모바일에서 목업 폴백을 제거하고 **실데이터만 렌더링**하도록 정리해, 두 클라이언트의 동작을 일치시킴

## 4. "설정만 있고 안 오는 알림" → 개인화 실발송 파이프라인

**문제**
알림 설정 UI는 있었지만 실제로 발송되는 로직이 없었다(`TODO`에 명시). 또 외화 구독은 환율에 따라 실질 부담이 달라지는데 사용자가 이를 체감하기 어려웠다.

**의사결정**
Frankfurter 환율 API로 외화 구독을 **KRW로 자동 변환**하고, "결제 N일 전 / 환율 급등 / 예산 초과 / 중복 구독 / 가격 인상"을 **사용자 설정 기반으로 개인화**해 실제 발송하도록 알림 시스템을 구현.

**해결 / 결과**
- 단순 CRUD 앱을 넘어 **선제적으로 돈 새는 지점을 알려주는** 서비스로 차별화
- 알림 종류·시점을 사용자별 `notification_settings`로 제어해 스팸이 아닌 유의미한 알림만 전달

## 5. 개인 프로젝트라도 인증은 프로덕션 기준으로 → 보안 하드닝

**문제**
로그인·회원가입은 흔한 공격 표면(무차별 대입, 사용자 열거, 시크릿 노출). 데모 수준이 아니라 **실제 배포 가능한 수준**으로 만들고 싶었다.

**의사결정 → 해결**
- **사용자 열거 방지**: 로그인 실패를 401로 통일 + 응답 타이밍 완화
- **무차별 대입 차단**: slowapi로 로그인 10회/분, 회원가입 5회/분 rate limiting
- **비밀번호 강도 검증**: 최소 8자 + 영문 + 숫자
- **시크릿 분리**: `SECRET_KEY`·DB 비밀번호를 환경변수화(기본값 사용 시 기동 경고, `.env.example` 문서화)
- **프록시 스푸핑 대비**: `X-Forwarded-For` 신뢰를 `TRUST_PROXY` 플래그로 제어(기본 off)

**결과**
보안 동작에 맞춰 테스트를 갱신하고, **웹 nginx 컨테이너 + CORS/DB 비밀번호 환경변수화**로 운영 배포 구성까지 완료. "돌아가는 데모"가 아니라 **배포를 전제로 한 설계**임을 보여주는 파트.
