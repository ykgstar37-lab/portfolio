Technical Decisions
WebSocket 릴레이 서버를 왜 직접 구현했는가?
프론트엔드에서 Binance에 직접 연결하면 CORS 차단과 API 키 노출 문제가 발생합니다. FastAPI WebSocket 엔드포인트가 Binance 스트림을 수신하고 Set 기반 클라이언트 추적으로 브라우저에 브로드캐스트하는 릴레이 구조를 설계했습니다.
GARCH 모형을 매 요청마다 적합(fit)하지 않은 이유는?
arch 라이브러리의 적합은 수십~수백ms가 걸립니다. 인메모리 캐싱(5분 TTL)으로 반복 호출을 방지하고, 120일 윈도우로 입력을 제한하여 응답 속도를 확보했습니다. 개별 모형 실패 시 0.0을 반환하여 에러를 격리했습니다.
5개 모형 중 "최적 모형"을 고정하지 않은 이유는?
시장 구간마다 최적 모형이 달라집니다. 모형을 하나로 고정하는 대신, 60일 롤링 RMSE로 실시간 리더보드를 운영하고 백테스트로 구간별 최적 모형을 탐색할 수 있게 했습니다.

모형 진화

GARCH(1,1) → TGARCH(비대칭) → HAR(다중 시간축) → HAR-TGARCH(결합) → HAR-TGARCH-X(+외생변수). 단계적으로 복잡도를 올리며 성능 변화를 추적.

01
CryptoVol Dashboard

분석 모형을 실시간 서빙 API로 전환하며 모델 서빙 설계를 체득

Problem

GARCH 변동성 예측 모형을 실시간 API로 서빙하려니, 모형 적합(fit) 연산이 수백ms — 동시 요청 시 추론 지연 발생. 모델 재계산 비용이 높아 서빙 안정성 확보가 핵심 과제.

Solution

5분 TTL 인메모리 캐싱 + 120일 윈도우 제한으로 재계산 방지. FastAPI WebSocket 릴레이 서버 구현. Promise.all로 API 호출 병렬화.

Result

14 REST + 1 WS 엔드포인트 / 1개 모형 실패 ≠ 전체 장애(에러 격리) / WebSocket 릴레이로 API 키 노출 차단

Insight

"모델을 만드는 것"과 "모델을 안정적으로 서빙하는 것"은 완전히 다른 설계 관점 — 캐싱, 에러 격리, 보안 아키텍처가 서빙 안정성의 핵심.

#모델서빙#캐싱전략#추론최적화#에러격리
02
PyMate

Embedding 모형 차원 교체와 Reranker 경량화로 RAG 서빙 품질 최적화

Problem

Embedding 768D에서 Context Precision 0.83 정체. Reranker(BAAI/bge-reranker-v2-m3) 레이턴시가 응답 속도를 저하. Flask MVP의 프로덕션 한계.

Solution

text-embedding-3-large(3,072D)로 교체 + Qdrant 재설계. Reranker를 cross-encoder/ms-marco-MiniLM-L6-v2로 경량화하여 레이턴시 -1초. 이중 쿼리(KO+EN) 전략으로 recall 개선.

Result

Context Precision 0.83→0.97(+14.4%) / Context Recall 0.70→0.79(+12.7%) / Reranker 레이턴시 -1초 / 병목 원인을 "LLM"→"embedding 품질"로 재정의

Insight

RAGAS로 검색·생성을 분리 측정하여 병목이 "LLM 답변 능력"이 아닌 "embedding 검색 품질"임을 특정. 서빙할 모형 선택이 곧 전체 성능 — 구조를 바꾸는 것이 기능 추가보다 서비스 품질에 큰 영향.

03
WorkFlow Agent

vLLM 기반 sLLM 서빙과 출력 검증 시스템 설계

Problem

Base 모델에 "인턴에게 AWS 접근 권한을 줘도 되나요?" 질의 시, "yes"(오답) + confidence 0.92(과신) + "제12조"(미존재 조항 환각) 반환. 기본 정확도 37.2%. LoRA v2에서 98건 추가 시 -3.2%p 하락 — 라벨 오염.

Solution

4중 Guardrail + 5-factor Confidence 보정. 동일 쿼리에서 "conditional"(정답) + confidence 0.78(적절) + 실존 조항 2건 + 조건·대안 제시로 개선. LoRA v3는 19건만 약점 정밀 타겟팅.

Result

판단 정확도 37%→85% / 환각(미존재 조항) → 실존 근거 2건 인용 / GPT API 의존 제거 → vLLM 프라이빗 서빙(비용 절감 + 데이터 보안)

Insight

같은 쿼리에서 Base는 오답+환각+과신, LoRA+Guardrail은 정답+실존근거+적절한 confidence. 공통 LLM 모듈로 provider 전환 1줄. 외부 LLM 출력을 서버가 검증하는 설계 원칙 확립.
