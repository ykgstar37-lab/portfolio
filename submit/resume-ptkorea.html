  • 문제 정의: 모든 요청에 전체 데이터 검색을 태우면 비용이 높고 응답 지연. "안녕"과 "강남구 박물관 추천"을 같은 파이프라인으로 처리하는 것은 리소스 낭비.

데이터 검색 파이프라인의 품질을 RAGAS 4개 지표로 분리 측정하여 병목 특정. 담당: Qdrant 벡터 DB 설계, 임베딩 차원 최적화, Django + AWS EC2 프로덕션 배포.
  • 문제 정의: "검색 결과가 부정확"의 원인이 파이프라인 어느 단계인지 불분명. RAGAS로 측정한 결과, 생성 충실도(Faithfulness)는 높지만 검색 정확도(Context Precision)가 낮음 → 병목은 데이터 임베딩 품질로 재정의.
  • Solution: 임베딩 768D→3,072D 교체 + Qdrant 재설계. Reranker cross-encoder 경량화(레이턴시 -1초). Flask→Django 전환. AWS EC2 + Nginx + Gunicorn 소켓 바인딩 직접 구성.
  • Result: Context Precision 0.83→0.97(+14.4%) · Context Recall 0.70→0.79(+12.7%) · Reranker -1초 · AWS 안정 배포(502 에러 해결).
"결과가 안 좋다"는 증상이지 진단이 아니다 — 각 단계를 지표로 분리 측정해야 병목을 특정할 수 있다.
