Role Fit

왜 뤼튼 Agent Developer 인턴인가

뤼튼 AX CIC는 공식 공고에서 Human-like Agent와 Productivity Bottleneck 해결을 이야기합니다. 저는 모델 성능 자체보다 "실무에서 무엇이 병목이고 무엇이 오답을 유발하는가"를 정의해 구조로 고친 경험이 있어, 이 포지션의 문제 정의 방식과 잘 맞는다고 생각합니다.

01측정 → 재정의 → 개선

PyMate에서 "답변 품질이 낮은 건 LLM 때문"이라는 팀 가정을 RAGAS 평가셋으로 검색·생성 단계를 분리 측정해 반증했습니다. 결론은 임베딩 차원 문제였고, 768D→3,072D 교체 한 번으로 Context Precision +14.4%p가 나왔습니다. 감이 아니라 숫자로 병목을 다시 그리는 작업 습관이 있습니다.

02실패한 실험에서 판단 기준 뽑기

WorkFlow Agent LoRA v2에서 데이터를 98건 더 넣었더니 정확도가 -3.2%p 하락했습니다. "더 많이 = 더 좋음"이 틀렸다는 걸 실험으로 확인한 뒤, v3는 오답 로그에서 19건만 골라 약점 타겟팅으로 재설계 → +2%p 회복. 이 경험이 이후 모든 데이터 판단의 기준이 됐습니다.

03"틀릴 때의 거동"까지 설계

sLLM이 존재하지 않는 조항을 confidence 0.92로 인용하는 문제를 만난 뒤, 4중 Guardrail(키워드·조항 존재·카테고리·일관성)과 5-factor Confidence 보정을 설계했습니다. 정확도 37→85%, JSON 유효율 70→97%, 과신뢰 오분류 69%↓. 모델이 아니라 시스템으로 신뢰성을 만들 수 있다는 감각이 있습니다.

1. 시작 배경과 목표

  • 단순한 챗봇이 아니라, 실제 판단 보조에 쓸 수 있는 Agent를 만들고 싶었습니다.
  • 목표는 "정답을 잘 말하는 모델"이 아니라 "틀릴 때도 위험하게 굴지 않는 시스템"을 만드는 것이었습니다.
  • 따라서 정확도뿐 아니라 JSON 유효성, confidence calibration, 환각 발생 여부를 함께 봐야 한다고 정의했습니다.

2. 팀 4명 분담과 내 단독 책임 영역

  • 팀 구성: 신지용(PM·오케스트레이터), 문지영(FE·Intent LoRA), 안혜빈(BE·FastAPI·DB·인증), 윤경은(AI·판단 Agent·RAG·LoRA 파인튜닝).
  • 내 단독 산출물: ① 판단 Agent 구조 설계, ② 4중 Guardrail 구현, ③ 5-factor Confidence 보정 로직, ④ LoRA v1→v3 데이터셋 설계(총 3,468건), ⑤ 공통 LLM 모듈(provider 패턴) — GPT/Claude/vLLM을 1줄 교체로 전환 가능하게 통일, ⑥ vLLM+RunPod A100 서빙 인프라.
  • 공동 작업: Intent 분류 라벨링(문지영과 라벨 기준 협의), LangGraph 오케스트레이터 흐름 통합(PM과).

3. 판단 근거 — "왜 이 숫자인가"

  • 왜 "4중" Guardrail인가: 오답 패턴을 분류해보니 ① 질문의 핵심 키워드 누락, ② 존재하지 않는 조항 인용, ③ 다른 카테고리 규정을 끌어옴, ④ 같은 문서 내 앞뒤 모순 — 네 종류가 전부였습니다. 3중으로는 ④번을 잡을 수 없었고, 5중부터는 직교성이 무너져 중복 감지가 발생해 4개로 고정했습니다.
  • 왜 LoRA v3 데이터를 19건으로 줄였나: v2에서 98건을 추가 보강했더니 정확도가 오히려 -3.2%p 하락했습니다. 라벨 오염이 원인이었고, v2 오답 로그를 전수 분석해 conditional/규정 교차 판단 약점에 해당하는 19건만 뽑아 재설계 → +2%p 회복. "양 < 질"을 실험으로 증명한 뒤부터는 데이터 추가 전에 약점 분류를 먼저 합니다.
  • 왜 RAG 컨텍스트를 학습에 안 넣었나: 초기에 RAG 결과를 학습 데이터에 섞었더니 노이즈로 -9.8%p 급락. "학습은 하드코딩된 깨끗한 데이터, 서빙은 RAG 정제 삽입"으로 분리한 뒤 안정화됐습니다.
  • Label Smoothing 0.1 + 7단계 실험: confidence 0.95로 과신하는 Intent 분류 오류를 7회 반복 실험으로 좁혀 오분류 69%↓, F1 97.88% 달성.

4. 결과와 산출물

  • 정확도 37%→85%, JSON 유효율 70%→97%, confidence 0.92 과신 응답을 0.78로 보정
  • RAG: HyDE + BM25/Vector + RRF(k=60) + Reranker 9단계 파이프라인으로 규정 10개 문서 교차 검색
  • 문서 파싱: Docling + PaddleOCR + python-docx 라우터로 PDF/DOCX/스캔 이미지 3종 지원
  • FastAPI + LangGraph + vLLM + LoRA + Qdrant + Docker + AWS EC2 + RunPod A100 배포

5. Retrospective — 아쉬운 점 / 다음에 하고 싶은 것

  • [높음] conditional(재량적 표현) 정확도 78% — 목표 85% 대비 -7%p 미달. 경계가 모호한 케이스(예: "필요한 경우", "원칙적으로")에서 판단이 흔들렸고, 학습 데이터를 더 수집해야 합니다.
  • [중간] 멀티턴 미지원 — 단건 Q&A 구조로 세션 맥락이 끊깁니다. 다음 버전에서는 세션 메모리와 이전 턴 참조 구조를 추가하고 싶습니다.
  • [낮음] Reranker가 응답에 +5.7초를 더합니다. 비동기 Reranking이나 top-k 캐싱으로 체감 속도를 개선할 여지가 남아 있습니다.
  • 핵심 인사이트: Agent 시스템은 "잘 답하는 능력"만큼 "틀릴 때의 거동"이 중요합니다. LLM 출력은 신뢰 대상이 아니라 검증 대상이라는 원칙을 이 프로젝트에서 체득했습니다.

Seoul Culture Map

Role Fit · Agent Routing & 비용 최적화

"모든 요청에 LLM을 태울 필요는 없다"는 가정으로 3-node 라우팅을 설계해 요청당 비용을 $0.003 — 단일 LLM 호출 대비 85% 절감했습니다.

학술제 R 군집분석 결과가 PDF로만 남아 아무도 활용하지 못했던 경험에서 출발했습니다. "분석이 끝나는 순간 가치도 끝나는 상태"를 문제라고 정의하고, 서울시 문화시설 2,500+개를 탐색·추천하는 Intent 라우팅 기반 RAG 서비스로 확장했습니다. 전 과정을 개인으로 설계·구현·배포했습니다.

문제와 접근 — 왜 3-node 분리인가

  • 단일 LLM 호출 파이프라인은 일상 대화("안녕")에도 검색·생성을 전부 태워 비용이 일정하게 높습니다.
  • Intent → Retrieve → Generate로 분리하면 chitchat은 Retrieve를 스킵하고, Retrieve 단계는 LLM 없이 SQL + ChromaDB만으로 동작합니다. LLM 호출은 Generate 1회로 수렴.
  • 결과적으로 요청당 비용이 ~$0.003으로 떨어졌습니다(엔터프라이즈 단일 LLM 호출 기준 대비 85%↓). 측정은 평균 트래픽 시나리오에서 토큰 사용량 실측 기준.

내 판단과 결과

  • 로컬 임베딩 선택: OpenAI embedding 대신 all-MiniLM-L6-v2(384D, 33MB)를 로컬로 돌려 월 API 비용 $0. 200건 배치 처리로 메모리 부담을 줄이고, DB 대비 변화 10% 이내일 때 재임베딩을 스킵하는 로직으로 서버 재시작 시 30~60초 절약.
  • 2개 공공 API 통합: 서울 열린데이터광장(시설 데이터 풍부, 이미지 없음) + 한국관광공사 Tour API(관광지·사진). 좌표 필드명·카테고리 코드가 완전히 달라 정규화와 중복 제거 파이프라인을 설계해 2,500+ 시설 + 1,177장 이미지 확보.
  • 산출물: LangGraph 3-node Agent, ChromaDB+SQLite, SSE 스트리밍, 11개 REST API, pytest 15개, Leaflet 지도 + K-means 군집 시각화, FastAPI + AWS EC2 배포.

Retrospective — 아쉬운 점

  • [높음] 다국어(i18n) 미지원 — 외국인 관광객 대상 서비스인데 한국어만 구현. 다음 버전 1순위.
  • [중간] TypeScript 미도입 — 좌표 필드명 불일치 같은 런타임 버그를 컴파일 타임에 잡을 수 있었을 것.
  • 핵심 인사이트: Agent routing은 "언제 LLM을 호출할지"를 고르는 비용 판단 문제입니다. 이 감각은 뤼튼 Productivity Agent처럼 트래픽이 큰 서비스의 비용 설계를 이해하는 데 이어질 수 있다고 생각합니다.

PyMate

Team 4명 · 2026.01 - 2026.02

Role Fit · 측정 우선 · 병목 재정의 · 배포 안정화

"LLM이 문제"라는 팀 가정을 RAGAS 평가셋으로 반증하고, 검색 단계로 병목을 다시 정의해 Precision 0.83→0.97, Recall 0.70→0.79로 개선했습니다.

"답변이 부정확하다"는 피드백이 반복됐지만 원인은 아무도 몰랐습니다. 저는 이 문제를 "증상과 원인을 분리해야 한다"로 다시 정의하고, RAGAS로 검색(Context Precision/Recall)과 생성 단계를 분리 측정하는 구조를 팀에 제안했습니다.

판단 근거 — "왜 이 숫자인가"

  • 왜 임베딩 교체부터 했나: RAGAS 측정 결과 Context Precision 0.83이 병목이었습니다. 생성 단계(Answer Relevancy)는 이미 양호했기 때문에 LLM 교체는 무의미하다고 판단했고, 검색 품질을 먼저 건드렸습니다.
  • 왜 768D → 3,072D인가: 중간값(1,024D, 1,536D)도 후보였지만, text-embedding-3-large(3,072D)가 한국어 교육 도메인 용어(Python 문법·자료구조)를 더 잘 붙잡는다는 것을 평가셋에서 먼저 확인한 뒤 교체. 단일 교체로 Context Precision +14.4%p.
  • 왜 Reranker를 경량화했나: bge-reranker-v2-m3는 정확하지만 응답이 무거웠습니다. ms-marco-MiniLM-L6-v2로 교체해 약 -1초. 정확도 손실은 평가셋에서 무시할 수준임을 미리 확인.

내 단독 기여 (팀 4명 중)

  • RAG 파이프라인 설계(HyDE + BM25 + Cross-encoder Reranker, 관련도 3단계 라우팅), RAGAS 평가셋·측정 구축, 임베딩 교체 의사결정, Flask→Django 마이그레이션, Nginx+Gunicorn 502 디버깅, AWS EC2 배포.
  • 공동: Quiz API 3종(객관식/O·X/단답형) 설계.

배포 장애 해결 — "로컬은 되는데 AWS에서 502"

  • 로컬에서 잘 동작하던 코드가 AWS EC2에서 502를 반환. Nginx → Gunicorn → Django로 이어지는 소켓 경로 설정이 원인이었습니다. 요청 흐름을 단계별로 끊어 추적해 소켓 경로를 수정하고 배포 완료, 이후 장애 0건 운영.
  • 이 경험이 Seoul Culture Map과 WorkFlow Agent 배포를 혼자 책임질 수 있었던 기반이 됐습니다.

PyMate에서 "모델부터 바꾸자"는 팀 압박을 RAGAS 측정으로 반증한 경험이 있습니다. 이후로는 측정 인프라가 있거나 그걸 만들 자유가 있는 팀을 우선합니다. 두 번째는 주니어라도 문제 정의 단계에 참여할 수 있는지 — WorkFlow Agent에서 Guardrail 구조를 직접 제안·설계한 경험이 성장의 결정적 순간이었기 때문입니다.

왜 뤼튼인가

공식 할루시네이션 문서에서 "잘못된 답변·긴 맥락 손실·파인튜닝으로 정확도 개선"을 다루는 걸 봤습니다. 이 세 가지는 제가 WorkFlow Agent에서 Guardrail·confidence 보정·LoRA v3로 다뤄본 문제와 결이 닿아 있습니다. 공고가 말하는 Productivity Bottleneck이 추상적 구호가 아니라, 제가 관심 있게 다뤄 온 문제와 연결된다는 점이 지원 동기입니다.

중장기 목표

모델을 붙이는 사람이 아니라, Agent의 판단 흐름과 검증 체계를 함께 설계하는 엔지니어가 되고 싶습니다. 장기적으로는 실무형 Agent의 신뢰성과 운영 안정성을 책임지는 백엔드/AI 엔지니어로 성장하고 싶습니다.

Quick Notes

이 문서에서 강조한 키워드

뤼튼 Agent Developer 인턴 지원에 맞춰 선택적으로 더 강조한 역량들입니다.

빠른 스택 전환 (과거 실적)

7개월간 Flask → Django(PyMate), LangChain → LangGraph(PyMate→WorkFlow Agent), OpenAI API → vLLM+LoRA 자체 서빙(WorkFlow Agent), ChromaDB → Qdrant 전환을 전부 실전 투입했습니다. 새 스택을 "공부하고 붙이는" 게 아니라 "트레이드오프 비교 후 교체"하는 패턴이 익숙합니다.

정량 검증 습관

정확도, Context Precision/Recall, JSON validity, confidence calibration, 요청당 비용, 첫 토큰 지연 — 6종 지표로 개선을 설명합니다. "좋아졌다"가 아니라 "0.83→0.97, +14.4%p"로 말할 수 있습니다.

실험에서 배포까지

세 프로젝트 전부 프로토타입 → FastAPI/Django 서버 → AWS EC2 배포 → 장애 대응까지 제가 직접 다뤘습니다. Nginx+Gunicorn 502, vLLM+Docker+A100 서빙, SSE 스트리밍 디버깅 경험이 있습니다.

01할루시네이션 게이트 — 공식 문서 문제의식과 직결

02비용 통제 — 트래픽이 큰 Productivity Agent에 Intent 라우팅

Seoul Culture Map에서 일상 대화는 Retrieve를 스킵하는 3-node 라우팅으로 요청당 비용을 $0.003 (단일 LLM 호출 대비 85%↓)으로 낮췄습니다. 뤼튼 Productivity Agent처럼 트래픽이 많은 서비스에서도, "단순 명령 vs 추론 필요"를 나누는 사고가 비용 설계에 도움이 될 수 있다고 생각합니다. baseline을 측정하고 어떤 분기가 실제로 의미 있는지 배우며 기여하고 싶습니다.

03기억 관리 — Supporter 기억 업데이트 메커니즘과 연결

뤼튼 「서포터 기억을 관리하는 법」 문서에서 최근 대화 기반 자동 업데이트와 사용자 관리 기능을 봤습니다. 이는 WorkFlow Agent의 "학습과 서빙 분리(RAG 컨텍스트를 학습에 넣으면 -9.8%p)" 경험과 같은 결의 문제입니다. 어떤 상태를 장기 기억으로 승격할지, 어떤 노이즈를 막을지 기준을 세우는 과정에 관심이 있고, 측정 없이는 개선도 없다는 원칙 위에서 배우며 참여하고 싶습니다.
